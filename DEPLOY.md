# Deploying to Render — everything on Render

Live deployment for the Todo List Management System, all on Render:

```
React frontend (Render Static Site, free)
        ↓ VITE_API_URL = https://<backend>.onrender.com/api
Spring Boot backend (Render Web Service, Docker, free)
        ↓ Render Postgres (internal connection, `prod` profile)
PostgreSQL (Render managed database, free)
```

No Aiven, no other provider. The backend uses the `prod` Spring profile on
Render (`SPRING_PROFILES_ACTIVE=prod` in `render.yaml`), which switches the
database from MySQL to PostgreSQL — see
`backend/src/main/resources/application-prod.properties`. **Local development
is unchanged:** without the `prod` profile the app still uses your local MySQL,
exactly as before.

**Free-tier limits to know before you start:**
- The free web service spins down after 15 minutes without traffic, so the
  first request after idle takes ~30–60 seconds to wake up. Starter ($7/month)
  keeps it always on.
- **The free PostgreSQL plan expires after 30 days, and its data goes with it.**
  It is fine for trying the deployment out. If you want to keep your tasks
  past 30 days, upgrade the database to a paid plan in the Render dashboard
  before day 30, or export your data first.
- Nothing in this repo contains a real password or secret.

## 0. What is already done in the repo

- `backend/Dockerfile` — multi-stage Maven build, slim Java 17 runtime, low-memory JVM flags for the 512 MB free tier.
- `render.yaml` — Render Blueprint creating the Postgres database + backend web service + frontend static site, with the database wired into the backend automatically (`fromDatabase`).
- `backend/pom.xml` — PostgreSQL driver added (MySQL driver kept for local dev).
- `backend/src/main/resources/application-prod.properties` — Postgres datasource + dialect, activated only with `SPRING_PROFILES_ACTIVE=prod`.
- `backend/src/main/resources/schema-postgres.sql` — Postgres DDL if you ever want it explicitly (the backend creates the tables automatically with `ddl-auto=update`).
- `frontend/src/api/axios.js` — API base URL already comes from `VITE_API_URL`, so no code change is needed for production.
- `docker-compose.yml` — local Docker run now uses Postgres too, matching production (`docker compose up --build`).

## 1. Deploy everything with the Blueprint

1. Render Dashboard → **New → Blueprint** → connect your GitHub repo
   `vinaymekala04/todo-list-management-system`.
2. Render reads `render.yaml` and shows the three resources it will create:
   `todo-db` (Postgres, free), `todo-backend` (web service, free),
   `todo-frontend` (static site, free). Confirm — **no paid plan is selected**.
3. Wait for the database to be created and the backend to build and go Live.
   Note the backend URL, e.g. `https://todo-backend-xxxx.onrender.com` — the
   `xxxx` suffix is assigned by Render.
4. Test it: `https://<backend>.onrender.com/api/dashboard/summary` should return
   `401` without a token (that means the API is up and security is working).

## 2. Set the remaining env vars

The database connection and `JWT_SECRET` are already wired/generated by the
Blueprint. Fill in these on the Render dashboard:

**Backend service (`todo-backend`) → Environment:**
| Variable | Value |
|---|---|
| `CORS_ALLOWED_ORIGINS` | your frontend URL — fill this in after step 3, e.g. `https://todo-frontend.onrender.com` |
| `MAIL_HOST` / `MAIL_PORT` | `smtp.gmail.com` / `587` (already set by the Blueprint, for the 8am reminders) |
| `MAIL_USERNAME` / `MAIL_PASSWORD` | your Gmail address + Gmail **App Password** (never your normal password) |
| `MAIL_FROM` | same as `MAIL_USERNAME` |

**Frontend static site (`todo-frontend`) → Environment:**
| Variable | Value |
|---|---|
| `VITE_API_URL` | `https://<backend>.onrender.com/api` (your backend URL from step 1 + `/api`) |

Rebuild the frontend after setting `VITE_API_URL` — Vite bakes it in at build
time, so changing it needs a manual redeploy.

## 3. Wire frontend and backend together

1. Set `CORS_ALLOWED_ORIGINS` on the backend to the exact frontend URL
   (no trailing slash) and save — Render redeploys the backend automatically.
2. Open the frontend URL, register / log in, create a task. If login fails with
   a CORS error in the browser console, the `CORS_ALLOWED_ORIGINS` value does
   not exactly match the frontend URL — fix it and wait for the redeploy.
3. Your local data is **not** copied to Render — the Render database starts
   empty. Register a fresh account on the live site and re-create your tasks
   there (or export/import them later if you need the local ones).

## 4. Check the daily email reminders in production

- The scheduled job runs at 08:00 in the server's timezone, but **only while
  the backend is running**. On the free tier the service spins down when idle,
  so the 8am run may not fire if nothing woke the service — that is a free-tier
  limit, not a bug. The Starter plan ($7/month) keeps it always on.
- To test immediately in production, use Postman (the button was removed from
  the UI on purpose):
  ```
  POST https://<backend>.onrender.com/api/alerts/send-reminders
  Authorization: Bearer <your JWT from login>
  ```
  → `{"sent":1,"failed":0,"message":"Reminder email sent to ..."}`
  Calling it twice the same day returns `sent: 0` — tasks already reminded today are skipped.

## Troubleshooting

- **Backend build fails on Render:** check the deploy logs; the usual cause is
  the Dockerfile path — it must be `./backend/Dockerfile` with context `./backend`.
- **DB connection errors:** the backend must be running with
  `SPRING_PROFILES_ACTIVE=prod` (set by `render.yaml`). Without it, it tries
  MySQL on localhost and fails on Render.
- **Frontend shows a blank page / API errors:** `VITE_API_URL` was set after the
  build — change the env var and trigger a manual redeploy (Vite embeds it at build time).
- **Login works locally but not live:** CORS — see step 3.
- **First load is slow:** free-tier spin-down — wait ~60s and refresh.
- **Database gone after ~30 days:** the free Postgres plan expired — see the
  warning at the top. Upgrade to a paid plan before day 30 to keep the data.
